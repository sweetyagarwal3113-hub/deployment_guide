Service Worker & Browser Storage Architecture

A deep-dive technical reference on Service Workers, event-driven network proxies, Cache Storage API, offline PWAs, and the complete Client-Side Storage Ecosystem (Cache Storage, IndexedDB, sessionStorage, localStorage, Cookies, OPFS).

💡 What is a Service Worker?

A Service Worker is an event-driven JavaScript script that runs in a browser background thread completely separate from the web page's main UI thread (DOM).

It acts as a programmable network proxy sitting between your frontend web application, the browser's Cache Storage, and the network/server. It intercepts outgoing HTTP network requests, serves responses directly from cache when offline, processes background sync requests, and listens for server push notifications.

🔄 Service Worker Lifecycle (4 Phases)

Understanding the lifecycle is crucial to preventing stale cache traps and unexpected script behavior:

Phase 1: Registration

Executed by main thread JavaScript in your app (e.g. app.js):

main.js
if ('serviceWorker' in navigator) {
  window.addEventListener('load', () => {
    navigator.serviceWorker.register('/sw.js', { scope: '/' })
      .then(registration => console.log('SW Registered with scope:', registration.scope))
      .catch(err => console.error('SW Registration Failed:', err));
  });
}

Phase 2: Installation (`install` event)

Triggered when a new SW file is detected by the browser. Ideal for precaching core static App Shell assets:

sw.js
const CACHE_NAME = 'app-shell-v1';
const ASSETS_TO_CACHE = [
  '/',
  '/index.html',
  '/styles.css',
  '/app.js',
  '/offline.html',
  '/logo.svg'
];

self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then(cache => {
      console.log('[SW] Precaching App Shell assets');
      return cache.addAll(ASSETS_TO_CACHE);
    })
  );
  self.skipWaiting(); // Bypass waiting state and force new SW to activate immediately
});

Phase 3: Activation (`activate` event)

Triggered when the new SW takes active control of pages. Ideal for purging obsolete cache versions:

sw.js
self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then(cacheNames => {
      return Promise.all(
        cacheNames.map(cache => {
          if (cache !== CACHE_NAME) {
            console.log('[SW] Purging old cache:', cache);
            return caches.delete(cache);
          }
        })
      );
    })
  );
  return self.clients.claim(); // Take control of all existing open browser tabs immediately
});

Phase 4: Idle & Termination (Event-Driven Wakeup)

To conserve RAM and CPU, browsers shut down idle Service Workers after ~30 seconds of inactivity. The Service Worker automatically wakes up when triggered by events like fetch, push, or sync.

💾 Cache API & CacheStorage Deep Dive

The Cache API (CacheStorage) is a key-value storage mechanism designed to store Request and Response HTTP object pairs. It is accessible via window.caches in main scripts and self.caches inside Service Workers.

Core CacheStorage & Cache Methods

Method Description Code Example
caches.open(name) Opens an existing cache or creates a new one with the given name. Returns a Promise resolving to Cache object. const cache = await caches.open('v1-cache');
cache.add(request) Fetches a single URL from the network and stores the resulting HTTP Response in cache. await cache.add('/styles.css');
cache.addAll(requests) Fetches an array of URLs from network and stores all responses atomically. If any request fails, none are cached. await cache.addAll(['/', '/app.js']);
cache.put(req, res) Manually stores a custom Response object for a specific Request key without sending a new fetch request. await cache.put(event.request, networkResponse.clone());
cache.match(req, options) Searches for a matching cached response for a given request. Returns Response or undefined. const response = await cache.match(event.request);
cache.delete(req) Deletes an individual request/response entry from the cache. await cache.delete('/old-logo.png');
caches.delete(name) Deletes an entire named cache bucket. await caches.delete('v1-cache');
caches.keys() Returns names of all cache buckets for the origin. const keys = await caches.keys();

Storage Quota & Inspection

Cache storage limits depend on available device storage space (usually up to 60-80% of total free disk space per origin). You can query remaining space using the StorageManager API:

storage_quota.js
if ('storage' in navigator && 'estimate' in navigator.storage) {
  navigator.storage.estimate().then(({ quota, usage }) => {
    const quotaMB = (quota / (1024 * 1024)).toFixed(2);
    const usageMB = (usage / (1024 * 1024)).toFixed(2);
    const percentUsed = ((usage / quota) * 100).toFixed(2);
    console.log(`Storage used: ${usageMB} MB of ${quotaMB} MB (${percentUsed}%)`);
  });
}

⚡ Common Caching Strategies

Inside the fetch event listener, you implement network proxy routing using different caching patterns:

1. Cache First (Cache Falling Back to Network)

Best For: Static immutable assets (images, fonts, CSS, JS bundles). Returns cached response instantly; falls back to network only if cache miss.

sw.js (Cache First)
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then(cachedResponse => {
      if (cachedResponse) {
        return cachedResponse;
      }
      return fetch(event.request).then(networkResponse => {
        if (!networkResponse || networkResponse.status !== 200) {
          return networkResponse;
        }
        const responseToCache = networkResponse.clone();
        caches.open('runtime-assets').then(cache => {
          cache.put(event.request, responseToCache);
        });
        return networkResponse;
      });
    })
  );
});

2. Network First (Network Falling Back to Cache)

Best For: Frequently updated data (live feeds, news articles, API endpoints). Tries fresh network response first; falls back to cached backup when offline.

sw.js (Network First)
self.addEventListener('fetch', (event) => {
  event.respondWith(
    fetch(event.request)
      .then(networkResponse => {
        const responseToCache = networkResponse.clone();
        caches.open('dynamic-api-v1').then(cache => cache.put(event.request, responseToCache));
        return networkResponse;
      })
      .catch(() => {
        return caches.match(event.request);
      })
  );
});

3. Stale-While-Revalidate

Best For: Non-critical real-time content (user avatars, dashboard metrics). Serves cached response instantly for speed, while asynchronously fetching network data in background to update cache for the next page load.

sw.js (Stale-While-Revalidate)
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.open('sw-cache-v1').then(cache => {
      return cache.match(event.request).then(cachedResponse => {
        const fetchPromise = fetch(event.request).then(networkResponse => {
          if (networkResponse.status === 200) {
            cache.put(event.request, networkResponse.clone());
          }
          return networkResponse;
        });
        return cachedResponse || fetchPromise;
      });
    })
  );
});

4. Cache Only

Only searches cache. Fails if item is absent. Used for pre-built offline static shell apps.

5. Network Only

Bypasses cache completely. Standard web behavior for payments, authentication, and live web sockets.

🗄️ Client-Side Browser Storage Ecosystem

Modern web browsers provide multiple client-side storage mechanisms designed for different data types, persistence levels, and performance constraints.

Client-Side Storage Comparison Matrix

Storage Type Capacity Limit Persistence / Lifespan Service Worker Access API Style Data Formats Primary Use Case
Cache Storage Large (~GBs, Quota API) Persistent (until deleted) YES Async Promises HTTP Request / Response objects Network response caching, static asset precaching for offline PWAs
IndexedDB Large (~GBs, Quota API) Persistent (until deleted) YES Async Promises/Events Structured JSON objects, Blobs, ArrayBuffers, Files Complex offline application data, queued offline forms, transactional databases
sessionStorage ~5 MB per origin Tab session duration (cleared on tab close) NO Sync Blocking Strings only Transient multi-step wizard state, active form inputs for single session
localStorage ~5 MB to 10 MB per origin Persistent across tabs/reboots (until cleared) NO Sync Blocking Strings only (JSON stringify required) Lightweight UI user preferences, theme selection (dark/light), simple settings
Cookies ~4 KB total per domain (4096 bytes) Configurable (Expires/Max-Age) NO Sync (document.cookie) Formatted text string pairs Server authentication session identifiers, HTTP-Only security tokens
OPFS (Origin Private FS) Large (~GBs, Quota API) Persistent YES Async & Sync Access Handles Binary files, raw byte streams High-performance file processing, SQLite databases, WebAssembly storage

⚠️ Why are `localStorage` and `sessionStorage` Unavailable in Service Workers?

Service Workers run in a fully asynchronous, non-blocking event-driven global scope. localStorage and sessionStorage are synchronous blocking APIs. If accessed inside a worker thread, synchronous reads/writes would block the event loop, defeating the multi-threaded performance architecture.

Solution for Worker State: Use IndexedDB for structured state inside Service Workers, or communicate with browser tabs using postMessage or BroadcastChannel.

Sharing State Between DOM & Service Worker

Pattern A: Shared Storage (IndexedDB)

Both DOM scripts and Service Workers share access to the origin's IndexedDB stores.

Shared IndexedDB
// In DOM script:
const db = await idb.openDB('app-db', 1, { ... });
await db.put('tokens', tokenVal, 'authToken');

// In sw.js:
const db = await idb.openDB('app-db', 1);
const token = await db.get('tokens', 'authToken');

Pattern B: Bidirectional Messaging (`postMessage`)

Send runtime session tokens or state directly via postMessage messaging pipeline.

postMessage API
// In DOM script:
navigator.serviceWorker.controller.postMessage({
  type: 'SET_TOKEN',
  token: 'xyz123'
});

// In sw.js:
self.addEventListener('message', (event) => {
  if (event.data.type === 'SET_TOKEN') {
    authToken = event.data.token;
  }
});

🔔 Key Capabilities & Advanced PWA Features

📶 Offline UI Shell Pattern

Allows PWA apps to instantly render header, sidebar, and fallback UI pages even when network status is 100% offline.

🔔 Push Notifications (`push` event)

Listens for server push notifications via Web Push API and displays native OS system alerts even when browser tabs are closed.

🔄 Background Sync (`sync` event)

Defers failed offline form submissions or chat messages until stable internet connectivity is automatically re-established.

💬 Channel Communication (`BroadcastChannel`)

Enables seamless 1-to-many communication across all open tabs and active Service Workers using broadcast topics.

⚠️ Common Pitfalls, Gotchas & Security Rules

1. The Stale SW Cache Trap (Update Delay)

When updating sw.js, existing browser tabs run the OLD Service Worker until every single tab of your website is completely closed by the user. Call self.skipWaiting() during install and clients.claim() during activation to bypass this wait state.

2. Registration Scope Boundaries

A Service Worker script placed at /assets/js/sw.js can only intercept network requests starting with /assets/js/. Place your sw.js at the root directory level (/sw.js) to control the entire origin scope.

3. HTTP Header Cache-Control Danger

Never configure long HTTP Cache-Control response headers (e.g. max-age=31536000) on the sw.js file itself at the web server level. If cached by the server, browsers will fail to check for Service Worker code updates. Always serve sw.js with Cache-Control: no-cache, max-age=0.

4. HTTPS Requirement & Localhost Exception

Service Workers require HTTPS in production to prevent Man-in-the-Middle network tampering. Browser engines explicitly whitelist localhost and 127.0.0.1 to allow local development.
